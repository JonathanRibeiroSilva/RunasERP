### Graphify vs. implementation — documented discrepancies

- **Graphify insufficiency (TS import edges):** The graph was AST + doc-semantic with 0 LLM tokens spent on this run; TypeScript import-edge resolution is weak, so "No import cycles detected" is necessary-but-not-sufficient. I confirmed manually that there are no obvious cyclic imports, but Graphify alone could not prove it. (Evidence: Graphify + Manual.)
- **Per-file metrics absent from graph:** Component size, any counts, hook counts, direct-call counts are not represented as graph attributes — all such findings below are Manual.
- **Graph is whole-repo, backend-weighted:** ~85% of nodes/god-nodes are backend; the frontend is a thin, weakly-cohesive periphery. This itself corroborates the "no shared frontend layer" conclusion.

**The reconstructed frontend shape:** `App.tsx` (static route table) → page components → (directly) Axios, with a thin `AuthContext` for global auth state and a single real custom hook (`useCarrinho`). The spec's intended Component → React Query hook → API service → Axios data-flow does not exist.

## Findings

Severity scale: Critical (architectural/security risk or correctness bug) · High · Medium · Low. Each tagged with evidence source.

### C1 — Server-state library (React Query) is configured but completely unused — Critical · Both
**Evidence:** `useQuery|useMutation|useQueryClient|useInfiniteQuery` → 0 matches in src. Yet `QueryClientProvider` with staleTime/gcTime/retry is set in `main.tsx:15-24`. Graphify shows no React-Query hook nodes anywhere in the frontend.
**Affected:** every data page (Produtos, Clientes, Loja*, etc.).
**Root cause:** Data fetching was implemented ad hoc with useState/useEffect before/instead of adopting the configured RQ layer.
**Impact:** No caching, no request deduplication, no background refetch, no automatic invalidation, no built-in cancellation — all the benefits the spec relies on are absent. Every screen reinvents loading/error/empty handling. This is the single largest divergence from the spec.

### C2 — No API service layer; UI components call the network directly — Critical · Both
**Evidence:** 84 `api.*`/`apiPublica.*` calls across 23 files (e.g., `ProdutosPage.tsx:59`, `ClienteFormPage.tsx` 7 calls, `CheckoutPage.tsx` 12 calls). The spec's `services/api/{clientes,produtos,vendas,estoque,financeiro}Api.ts` modules do not exist — `services/api/` contains only `axios.ts`. Graphify: `apiPublica` recurs across page communities; no service god-node.
**Root cause:** Missing services/hooks layer; endpoints, params, and DTO shapes are inlined in components.
**Impact:** URL/param drift, no single place for error/response normalization, untestable data logic, high coupling of UI to transport.

### C3 — Axios client duplicated 12× (`apiPublica = axios.create`) — Critical · Both
**Evidence:** `axios.create` in 12 files — canonical `services/api/axios.ts:7` plus 11 copies in `useCarrinho.ts:5`, `CheckoutPage.tsx:14`, `GoogleCallback.tsx:7`, MicrosoftCallback, ClienteLoginPage, ClientePerfilPage, MeusPedidosPage, RastreamentoPedidoPage, ProdutoDetalhePage, LojaOnlinePublicoPage, ClienteLayout.
**Inconsistencies in the copies:** the canonical client uses `baseURL: env.apiUrl`; every `apiPublica` hardcodes `baseURL: '/api'`. Only CheckoutPage's copy adds a response interceptor; the others have none.
**Root cause:** No exported "public" client; copy-paste per page.
**Impact:** Cross-cutting concerns (auth redirect, timeout UX, error mapping) cannot be applied uniformly; behavior differs by page; 11 places to change for any client policy update.

### C4 — `CheckoutPage.tsx` is a 1,381-line god component (28 useState) — Critical · Manual
**Evidence:** 1,381 LOC (largest file by 3×; ~14% of all frontend code); 28 useState in one component; inline `apiPublica` + interceptor; inline types ClienteNovo/Endereco/Pagamento/Cliente/TipoEntrega/Step/ModoCheckout. Handles cart, login, registration, OAuth return, guest checkout, CEP lookup, freight, payment, and a 3-step wizard.
**Root cause:** No decomposition into step components/hooks; all concerns colocated.
**Impact:** Untestable, unsafe to change, high render cost, prime defect site (its own test file exists precisely because it's bug-prone — `__tests__/CheckoutPage.test.tsx`, 423 LOC).

### C5 — No Error Boundaries anywhere — Critical · Both
**Evidence:** `ErrorBoundary|componentDidCatch|getDerivedStateFromError` → 0 matches. Not present in `main.tsx` or `App.tsx`. Spec explicitly lists `components/common/ErrorBoundary/`.
**Impact:** Any render-time throw (e.g., reading `.detail` off an unexpected shape, mapping undefined) unmounts the whole React tree to a blank screen with no recovery. Combined with heavy any (F-H1), crash risk is real.

### C6 — Dashboard, Inventory, Sales, Financial (and Config) are placeholders, not implementations — Critical (scope) · Both
**Evidence:** `DashboardPage.tsx` uses hardcoded mockStats/mockAlerts and a "Gráfico será implementado em breve" placeholder — no API calls. `FinanceiroPage.tsx`, `EstoquePage.tsx`, `VendasPage.tsx` are 44-line "coming soon" screens; Configurações pages are 26–27-line stubs. Graphify clustered these stubs with shared infra (Comm. 42), not their domains.
**Impact:** 5 of the 11 functional modules in audit scope are non-functional. The audited "architecture" of those modules effectively does not exist yet — they must be greenfielded.

### H1 — Pervasive any and stringly-typed money; duplicated/conflicting domain & ApiError types — High · Both
**Evidence:** ~80 any occurrences across 29 files (e.g., `catch (error: any)` throughout, `errorLogger.ts` 7×, `useCarrinho.ts` 5×). `ApiError` is declared twice with different shapes: `types/common.ts:20` (`{detail, status_code}`) vs `types/auth.ts:46` (`{message, status?, detail?}`); `axios.ts` imports the auth one. Produto/Categoria/Cliente/Endereco are redefined inline in multiple pages (Graphify Comm. 36/60/69/99/151). Money fields typed as string in `useCarrinho.ts:19-28`. `ProdutosResponse` (`ProdutosPage.tsx:24`) uses skip/limit, diverging from the shared `PaginatedResponse` (page/size/pages) that no one imports.
**Impact:** No DTO/Entity/ViewModel separation; type drift between pages and backend; runtime-shape assumptions that error boundaries (C5) don't catch.

### H2 — Tables: client-side filtering over a single page + no debounce — High (correctness) · Manual
**Evidence:** `ProdutosPage.tsx:81-90` filters by search term and category on the client, against only the current 10-item page ("Filtro… feitos no cliente (backend não suporta ainda)"). Search is wired into a useEffect (`:53-55`) that refetches on every keystroke with no debounce (spec requires 300 ms). No sorting, row selection, or virtualization anywhere.
**Impact:** Search/filter silently miss matches that aren't on the current page (wrong results); pagination counts misrepresent filtered sets; unnecessary request volume.

### H3 — Broken/again-stale auth refresh in the interceptor — High · Manual
**Evidence:** `axios.ts:33-66`: on 401 it declares `_retry` but never sets it, never calls a refresh, and never retries the original request — it clears legacy localStorage and `window.location.href = '/login'`. The spec (§1) shows the interceptor refreshing then replaying the request. `authService.refreshToken` is a deprecated no-op.
**Impact:** A single expired-access-token 401 on any non-login request hard-redirects the user to login mid-task (lost form state), even though the refresh cookie may be valid. The "automatic refresh" claim in spec/README is false in code.

### H4 — No request cancellation; race conditions on unmount/refetch — High · Both
**Evidence:** `AbortController|signal|CancelToken|abort(` → 0 matches. Manual useEffect fetches (e.g., ProdutosPage on `[currentPage, searchTerm, categoriaFilter, statusFilter]`) set state after await with no abort.
**Impact:** Fast filter/typing or quick navigation produces out-of-order responses overwriting newer state, and setState-after-unmount warnings/leaks. React Query (C1) would have provided this for free.

### H5 — No route-level code splitting — High (perf/spec) · Both
**Evidence:** `lazy(`/`Suspense` → 0 matches. `App.tsx:1-24` statically imports all ~30 page modules; the entire app (including the 1,381-line checkout and unused chart libs) ships in one initial bundle. Spec's "Code Splitting" section is unimplemented.
**Impact:** Large first-load payload; public storefront users download the entire admin app.

### H6 — Shared component library is dead code; every page re-implements UI — High · Both
**Evidence:** `ResponsiveTable`/`ResponsiveCard`/`ResponsiveContainer` are defined and exported by `components/common/index.ts` but have zero imports from any page (only `MaskedInput` is imported, and only by CheckoutPage). Graphify isolates them as a disconnected island (Comm. 94). The spec's Button/Modal/Table/Pagination/Loading/ErrorBoundary/Card/Badge/ConfirmDialog mostly don't exist.
**Impact:** Duplicated raw `<table>`/card/badge/spinner markup in every page (e.g., ProdutosPage), inconsistent UX, no single styling/behavior contract — the opposite of the spec's design system intent.

### H7 — Stub feature routes have no permission protection — High (security) · Manual
**Evidence:** `App.tsx:174-181`: estoque, vendas, financeiro are reachable by any authenticated user. Only `configuracoes/*` is wrapped in `RoleProtectedRoute`. There are three independent role-check implementations: `AuthContext.hasRole` (`AuthContext.tsx:71`), `RoleProtectedRoute` (`RoleProtectedRoute.tsx:20`), and `Sidebar.canViewItem` (`Sidebar.tsx:133`). Permissions are coarse (ADMIN/OPERADOR only); no action-level permission gating exists.
**Impact:** Inconsistent enforcement; when these modules are built, the access model is undefined and duplicated logic will drift.

### M1 — Hardcoded tenant slug in the Sidebar — Medium · Manual
**Evidence:** `Sidebar.tsx:69`: `window.open('/c/distribuidora-central', '_blank') // TODO: Usar empresa_slug dinâmico`. ProdutosPage similarly builds `/c/default` (`ProdutosPage.tsx:47`).
**Impact:** Multi-tenant leak — every company's "Minha Loja" link points to one hardcoded store. Breaks the multi-tenant model the backend enforces.

### M2 — Debug logging left in production paths, including cookie contents — Medium (security/observability) · Both
**Evidence:** 64 `console.*` across 23 files. `useCarrinho.ts:70-71` logs `document.cookie`; OAuth callbacks log success/cookie status. tokenService/authService emit `console.warn` deprecation notices on use.
**Impact:** Noisy console, minor information disclosure, no structured/leveled logging, no gating by environment.

### M3 — No centralized error/empty/loading UX; native `confirm()`; dual toast systems — Medium · Both
**Evidence:** `confirm()` used in 8 files (e.g., `ProdutosPage.tsx:119`) instead of a ConfirmDialog. Two notification abstractions coexist: `Toast` from `utils/toast.ts` and raw `toast` from react-toastify are each imported across the 25 files that show notifications. Loading spinners, empty states, and error banners are bespoke per page.
**Impact:** Inconsistent feedback patterns; blocking native dialogs break the dark-mode design language; two toast configs can diverge.

### M4 — Observability is console-only; resilience utils wired to one screen — Medium · Manual
**Evidence:** `errorLogger.ts` has solid `isRetryableError`, `extractErrorMessage`, `sleep` (backoff) and a Sentry hook — but it's commented out and the function is named `logCheckoutError`; grep shows it's imported only by CheckoutPage. No request tracing / correlation IDs.
**Impact:** Useful resilience code benefits exactly one page; no production error reporting; incidents are invisible.

### M5 — Unused dependencies shipped — Medium · Both
**Evidence:** `chart.js`, `react-chartjs-2`, and `react-loading-skeleton` are in package.json but never imported (Dashboard charts are placeholder `<div>`s; spec's skeleton loading is unimplemented). `date-fns` usage not observed in sampled pages.
**Impact:** Bundle bloat and misleading "stack" documentation.

### M6 — Routing gaps: no 404 page; broad catch-all redirect — Medium · Manual
**Evidence:** `App.tsx:211` `path="*"` → `Navigate to="/dashboard"`. Spec lists a `NotFound/` page. No breadcrumbs exist (`Breadcrumb` → 0 matches), though spec/layout call for them.
**Impact:** Mistyped/legacy URLs silently bounce authenticated users to dashboard and unauthenticated users into the auth redirect loop; no deep-link error feedback; weaker navigational orientation.

### L1 — Stale documentation vs. secure implementation — Low · Both
**Evidence:** README states "Access Token: localStorage"; spec offers localStorage as MVP token storage. Reality is better: `tokenService.ts` is a deprecated no-op, tokens live in HTTP-only cookies (`axios.ts:13` withCredentials), and OAuth callbacks validate CSRF state and explicitly avoid localStorage (`GoogleCallback.tsx:33-60`). Spec also references Material-UI and `components/forms/`, `components/loja/` folders that don't exist.
**Impact:** Docs misrepresent both the security posture (understating it) and the structure (overstating it); onboarding confusion.

### L2 — Dead/compatibility code and minor unsafe access — Low · Manual
**Evidence:** tokenService (all no-ops), `authService.refreshToken` (no-op), `env.tokenRefreshThreshold` (unused). `Sidebar.isSubmenuActive`/initial-expand call `location.pathname.startsWith(subItem.path)` where path is optional (`Sidebar.tsx:125,160`) — coerces undefined, a latent bug. `toggleSubmenu`/`isMenuExpanded` carry unused params.
**Impact:** Cognitive overhead; latent edge-case defects.

### L3 — Accessibility is partial — Low/Medium · Both
**Evidence:** Forms use `htmlFor`/`aria-` (ClienteFormPage 15×, ClienteEnderecosPage 8×), and the mobile menu has `aria-label`. But icon-only action buttons rely on `title` only (`ProdutosPage.tsx:281-301`), there's no focus management on route/modal transitions, no skip-to-content, and native `confirm()` bypasses the design system.
**Impact:** Keyboard/screen-reader users get inconsistent affordances; falls short of the spec's WCAG-AA goal.

## Prioritized Backlog

Per instructions, these are audit groupings only — no code changes proposed. Each phase names what to address, not how.

### Phase 1 — Stop the bleeding (Critical correctness & resilience)
- **C5** Introduce error boundaries (app shell + per-route) — crash containment.
- **H3** Fix the 401/refresh interceptor (real refresh-and-retry vs. hard redirect).
- **H2** Server-side search/filter/pagination contract for tables (correctness bug).
- **M1** Remove the hardcoded distribuidora-central / default tenant slugs.
- **M2** Strip cookie/debug `console.*` from production paths.
- **H7** Define and apply route/action permission model to all real modules.

### Phase 2 — Establish the missing architecture (Critical structural)
- **C1 + C2 + C3** Adopt the intended layering: a single shared API client + per-domain service modules + React Query hooks; eliminate the 11 apiPublica copies and 84 inline calls.
- **H1** Centralize domain types (DTO/Entity/ViewModel), dedupe ApiError, retire any from catch/data paths, fix string-typed money.
- **H4** Request cancellation (delivered for free once RQ adoption lands).

### Phase 3 — Decompose & consolidate (High maintainability/UX)
- **C4** Break up CheckoutPage into step components + hooks.
- **H6 + M3** Build/adopt the real shared component library (Table, Pagination, ConfirmDialog, Loading/Empty/Error, Badge), retire dead Responsive* or fold their logic in, unify on one toast abstraction.
- **H5** Route-level code splitting (lazy/Suspense).
- **M4** Wire structured logging + error reporting (Sentry) app-wide; generalize logCheckoutError.

### Phase 4 — Complete scope, polish, and align docs (Medium/Low)
- **C6** Implement the stub modules (Dashboard real data + charts, Estoque, Vendas, Financeiro, Configurações) on the Phase-2 foundation.
- **M5** Remove or actually use unused deps (chart.js, react-chartjs-2, react-loading-skeleton).
- **M6** Add a real 404/NotFound page and breadcrumbs.
- **L3** Accessibility pass (focus management, labeled icon buttons, skip-nav, replace native dialogs).
- **L1/L2** Reconcile docs with the (better-than-documented) security reality; remove dead compatibility code and fix the Sidebar optional-path access.

## Evidence & Honesty Notes

**Audit boundaries / honesty notes:** Findings are evidence-backed via Graphify (architecture skeleton, duplication/cohesion signals, cycle check) and manual inspection (per-file metrics, code-level bugs). Where Graphify was insufficient — primarily TypeScript import-edge resolution and per-file metrics — manual inspection was used and labeled as such. Component-level findings were drawn from full reads of the core infrastructure plus representative pages (Checkout, Produtos, Cliente forms, Dashboard, stubs, layout, hooks, services); a minority of similar pages (e.g., several LojaOnlinePublico screens) were characterized by pattern via grep rather than full read, but all exhibit the same duplicated-apiPublica / manual-state / inline-types pattern confirmed in the files read in full.
